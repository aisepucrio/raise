## Celery task failure rules

When a Celery task fails:

* Save the task as `FAILURE` in the database.
* Save the real error message in `Task.error`.
* Save the exception class name in `Task.error_type`.
* Include enough metadata for the frontend to show what failed.
* Re-raise the exception or otherwise make Celery record the task as failed.
* Do not hide the real exception behind a generic `"returned no data"` message.
* Do not let `AsyncResult` later overwrite a true failure as success because the task returned an error dictionary normally.

Acceptable failure pattern:

```python
except Exception as e:
    error_msg = str(e)
    error_type = type(e).__name__

    task_obj.status = "FAILURE"
    task_obj.error = error_msg
    task_obj.error_type = error_type
    task_obj.operation = f"GitLab mining failed: {error_msg}"
    task_obj.save()

    self.update_state(
        state="FAILURE",
        meta={
            "operation": "fetch_gitlab_metadata",
            "project": project_identifier,
            "error": error_msg,
            "error_type": error_type,
            "exc_type": error_type,
            "exc_message": error_msg,
            "exc_module": e.__class__.__module__,
        },
    )

    raise
```

Avoid this pattern:

```python
except Exception as e:
    self.update_state(state="FAILURE", meta={"error": str(e)})
    return {"status": "FAILURE", "error": str(e)}
```

## GitLab API rules

* Support GitLab project identifiers in the format the UI/API documents.
* Treat GitLab project paths carefully: project paths such as `group/subgroup/project` must be URL-encoded when used as path parameters.
* Keep GitLab host configurable if the backend already has or needs self-hosted GitLab support.
* Prefer environment variables such as:

  * `GITLAB_TOKENS`
  * `GITLAB_API_URL`
* Do not hard-code private tokens.
* Do not log raw tokens.
* Token validation should be explicit and should produce user-facing errors.
* API requests should have timeouts.
* For paginated endpoints, follow GitLab pagination headers or response links using a small focused helper.
* Do not fetch unnecessary large fields unless the requested mining type requires them.
* For optional fields that may fail, save the main metadata and record/log the optional failure.
